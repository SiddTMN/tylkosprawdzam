# Audyt źródeł przyszłych wydarzeń BTC, ETH, DOT, XLM, ATH i BONK

Stan sprawdzenia: **13 października 2026**. Zakładam, że ATH oznacza **Aethir**, a BONK token ekosystemu Solana. Ticker sam w sobie nie jest wystarczającym identyfikatorem źródła.

**Wynik: istnieje darmowa, licencjonowana podstawa dla części wydarzeń BTC, ETH i XLM. Nie potwierdzono kompletnego darmowego zestawu dla wszystkich sześciu aktywów i wszystkich wymaganych kategorii.** Największe luki dotyczą partnerstw, produktów, ATH/BONK oraz licencji na dane hostowanych agregatorów i kalendarzy.

Audyt obejmuje odczyt lokalnego projektu, aktualnego `main` przez GitHub, metadanych i diffu PR #2, dokumentacji interfejsów, materiałów źródłowych oraz regulaminów. Nie uruchamiano kolektorów, testów, workflow ani wdrożeń. Nie zmieniono kodu ani istniejących danych. Ten dokument i pomocniczy panel źródeł są nowymi artefaktami badawczymi.

## Jak czytać ocenę

- **P — potwierdzona podstawa:** znaleziono licencję materiałów i udokumentowany kanał dostępu, odpowiednie dla wskazanego zakresu. Należy zachować warunki licencji i limity usługi.
- **N — niejasne:** dostęp techniczny albo subskrypcja są możliwe, ale nie potwierdzono pełnego zakresu regularnego pobierania, przechowywania i publicznego publikowania własnego kalendarza.
- **O — ograniczenie:** regulamin ogranicza automatyzację lub publikację, albo potrzebne dane są płatne. Odrzucone z bezpłatnego wariantu bez dodatkowego uprawnienia.

Ocena dotyczy konkretnego kanału. Licencja repozytorium nie przenosi się automatycznie na zewnętrzny Google Calendar, stronę organizatora lub API agregatora. Udokumentowane API pozwalające na odczyt nie musi pozwalać na redystrybucję. `robots.txt`, HTTP 200 i brak klucza nie są licencją.

## Najprostszy zestaw

**Rekomenduję GitHub REST jako wspólny transport źródeł projektowych oraz opcjonalne API Federal Register dla rynku:**

1. **BTC:** harmonogramy wydań Bitcoin Core; Optech jako opcjonalne, licencjonowane uzupełnienie zapowiedzi.
2. **ETH:** meta-EIP hardforku i oficjalne agendy `ethereum/pm`. Ten wariant ma lepszą ustaloną podstawę licencyjną niż obecny zewnętrzny ICS, choć wymaga parsera dat z agend i respektowania CC BY-SA.
3. **XLM:** Stellar Docs — tylko jawne terminy sieci; nie traktować Releases jako automatycznych zapowiedzi.
4. **Rynek, opcjonalnie:** Federal Register API dla przyszłych terminów regulacyjnych. Powiązanie wspólnej regulacji z sześcioma aktywami jest klasyfikacją redakcyjną, nie sześcioma osobnymi wydarzeniami.

GitHub REST bez uwierzytelnienia ma [60 zapytań/h na IP](https://docs.github.com/en/rest/using-the-rest-api/rate-limits-for-the-rest-api). Mały odczyt co 6 h jest wykonalny bez zewnętrznego klucza. Paginacja, współdzielone IP runnera, ETag, `Retry-After` i 403/429 nadal wymagają obsługi. Darmowe standardowe runnery w publicznym repo nie są gwarancją terminowości harmonogramu.

**DOT:** kolejny etap to odczyt on-chain na właściwej sieci i szacowanie terminów blokowych albo wyraźnie licencjonowane API operatora. Nie kwalifikuję go teraz jako gotowego składnika najprostszego automatu.

**ATH i BONK:** pozostawić uczciwe „brak zatwierdzonego źródła”. Najkrótszą drogą do pełnego pokrycia są kanały JSON/ICS od projektów z jawną zgodą na pobieranie co 6 h, cache, publikację faktów/linków/własnych opisów oraz przechowywanie wyników w publicznym repozytorium i historii Git. W audycie nie kontaktowano się z projektami.

Dla „wiarygodnych oczekiwań” dopuszczać oficjalny cel daty/kwartału, z oznaczeniem **planowany/szacowany**, źródłem i warunkami. Nie znaleziono darmowego, licencjonowanego feedu konsensusu analityków dla całej szóstki. Brak prognozy jest lepszy niż fikcyjna precyzja.

## Minimalne zasady przyszłego kalendarza

- Osobno przechowywać czas publikacji źródła, rzeczywisty czas weryfikacji i termin zdarzenia.
